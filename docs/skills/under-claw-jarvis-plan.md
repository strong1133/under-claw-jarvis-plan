# under-claw-jarvis-plan — 프롬프트 구성

> 이 문서는 스킬이 에이전트에게 **무엇을 지시하는지**를 파일 단위로 설명한다. 규칙의 정본은 각 파일이다.

복합 작업을 Intake → 이해 → 계획 → 구현 → 검수 순서로 진행하는 오케스트레이터다.
개발뿐 아니라 문서·분석·기획 산출물에도 같은 흐름을 적용한다.

## 파일 구성

| 파일 | 역할 |
|---|---|
| `commands/under-claw-jarvis-plan.md` | Claude Code 진입점 |
| `skills/under-claw-jarvis-plan/SKILL.md` | Codex 진입점 |
| `skills/under-claw-jarvis-plan/GEMINI.md` | Gemini 진입점 |
| `skills/under-claw-jarvis-plan/references/*.md` | 단계별 방법론 모듈 (세 진입점이 공유) |
| `skills/under-claw-jarvis-plan/shared/*.md` | 공통 작업 원칙·명세·검증·구성요소 (세 스킬 공통, 정본은 저장소 `shared/`) |

세 진입점은 같은 방법론을 가리키며, 호스트마다 다른 것은 작업 추적·스킬 호출·멀티에이전트 도구의 이름뿐이다(`references/05-host-map.md`).

## 진입점이 지시하는 것

| 절 | 내용 |
|---|---|
| 활성화 게이트 | 이름이나 명령으로 직접 호출됐을 때만 적용한다. 자동 로드됐다면 적용을 중단한다. |
| 공통 명세·증거·구성요소 | 시작 시 `shared/working-principles.md`를 읽고 전 단계에 적용한다. Intake에서 `shared/contract.md`로 명세를 확정하고, 검수 전 `shared/verification.md`로 증거를 검사한다. loop가 `resume_stage`를 넘기면 해당 단계부터 재수행한다. |
| 우선순위 | 일하는 방법은 이 스킬, 산출물 규약(코드 스타일·출력 언어·도메인 규칙)은 호스트 프로젝트 지침을 따른다. 호스트가 질문·승인·보고 방식을 명시하면 그것도 따른다. Karpathy 4원칙(가정 금지·단순성·외과적 변경·검증)을 전 단계에 적용한다. |
| 멀티에이전트 | 현재 세션의 서브에이전트로 council을 구성한다. 사고 단계는 독립 병행 → 교차 검토 → 합의 합성이다. 다른 모델 peer가 있으면 교차-모델로 확장한다. |
| 합의·검수 원칙 | 단계 시작 시 실제 참여자(`ACTIVE_PARTICIPANTS`)를 확정하고 전원 동의 없이 단계를 넘기지 않는다. 한 명이라도 `[BLOCK]`이면 진행하지 않는다. 작업자와 검수자를 분리하고, 분리 수단이 없으면 `DEGRADED_REVIEW`로 공개한다. |
| 구성 스킬 로깅 | 방법론 모듈을 적용하기 직전에 태그를 한 줄 남긴다(아래 표). 프로젝트 환경 스킬은 로깅 대상이 아니다. |
| 모드 분기 | 입력이 `test`면 `references/90-test.md`의 읽기 전용 자가진단만 수행한다. 단순 질의는 단계 게이트 없이 즉답한다. |
| HARD-GATE | 복합 작업은 시작 즉시 `[이해]` `[계획]` `[구현]` `[검수]` task를 만들고, 각 task는 모듈 적용·태그 로깅·Definition of Done 산출물이 모두 있어야 닫는다. brownfield는 3자 대조 전에 구현하지 않는다. 되돌리기 어려운 행위는 설계 합의 후에만 한다. 참여자가 둘 이상이면 독립 산출·유효 ACK·게이트 상태표를 요구한다. 같은 쟁점이 3회 초과 왕복되면 최소안을 임시 채택하고, 그래도 막히면 나머지 작업을 끝낸 뒤 최종 보고에 양안과 권장안을 담는다. |
| Phase 0 Intake | 입력에서 대상 프로젝트·최초 요구·교정 요청·정리 문서 경로·제약을 파싱한다. 묻기 전에 프로젝트 지침 문서를 읽는다. 이미 준 것은 다시 묻지 않고, 결과를 바꾸는 질문은 이 시점에 한 번에 모아 묻는다. 요약을 알린 뒤 응답을 기다리지 않고 진행하며, 이 요약이 시작 알림이다. |
| skill-map | 프로젝트 → 전역 순으로 커스텀 skill-map을 찾아 단계별 환경 스킬을 바인딩한다. 없으면 `60`의 유형 맵으로 동작한다. |
| 단계 회귀 | 후행 단계가 선행 단계의 누락을 드러내면 `<회귀 N→M>`을 남기고 선행 산출물만 갱신한 뒤 복귀한다. 같은 쟁점으로 2회 초과 회귀하면 가정을 채택해 기록하고 나머지를 끝낸 뒤 최종 보고에 담는다. |
| Definition of Done | 이해: 정렬된 요구와 성공 기준(brownfield면 3자 대조표). 계획: 저장된 설계 doc과 번호 매긴 task. 구현: task별 스펙·품질 리뷰 통과 기록. 검수: 실행 검증 결과와 마감 체크리스트. |
| 자율성 | 사소한 선택은 council이 정한다. 멈추는 경우는 파괴적·되돌리기 어려운 행동과 사용자가 결정해야 하는 실제 범위 변경뿐이다. 일부가 막혀도 나머지를 끝내고 못 한 부분과 이유를 보고한다. 요청과 관련 없는 문제는 고치지 않고 후속 항목으로 적는다. 위임한 동안에도 위임 결과에 의존하지 않는 작업을 계속한다. 내부 의견 왕복은 중계하지 않는다. |

## 공통 문서 (`shared/`)

| 파일 | 지시 내용 |
|---|---|
| `working-principles.md` | 표현(비유·수사 대신 직접 진술), 질문과 멈춤(Intake에서 한 번에 묻고 시작 후에는 가정으로 진행, 멈춤은 파괴적 행동과 실제 범위 변경뿐), 범위와 완료(범위 밖 문제는 보고만, 막힌 부분 외 전부 완료), 검증과 테스트 파일(실행으로 확인, 임시 코드 미보존, 테스트 파일은 요청·관례가 있을 때만), 위임 중 병행, 진행 보고(시작 한 줄·진행 알림·최종 정리). 각 스킬의 references와 어긋나면 이 문서가 우선한다. |
| `contract.md` | 명세 JSON 스키마(goal·scope·constraints·blocking_questions·criteria). 질문은 Intake에서 한 번에 묻고, 이후 생긴 질문은 가정으로 기록한다. 명세 해시를 실행·검수 기록에 묶는다. |
| `verification.md` | 실행 검증 → 의미 검수 → 합의 순서와 검수 보고 JSON. `evidence.py judge`가 보고의 일관성과 해시를 검사한다. |
| `components/ouroboros.md` | 명세 고정, 기계적 검증 우선, 회차 기록·재개, 자기 점수만으로 성공을 선언하지 않음. 원본 엔진을 중첩 실행하지 않는다. 태그 `<component:ouroboros 적용>`. |

## 입력과 출력

```text
/under-claw-jarvis-plan <요구사항>      # Claude
$under-claw-jarvis-plan <요구사항>      # Codex
/under-claw-jarvis-plan test           # 읽기 전용 자가진단
```

입력 형식은 자유다. Intake는 `- 이름: 경로` 목록, 최초 요구, 교정 요청, 정리 문서 경로, 제약 문구를 인식한다.
출력은 단계별 태그 로그, 설계 doc 파일, task별 리뷰 기록, 실행 검증 결과, 최종 보고다. Intake에서 정리 문서 경로를 받았으면 그 경로에 정리 문서를 쓴다.
