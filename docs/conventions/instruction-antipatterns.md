> "무엇을 넣을까"보다 **"무엇을 넣지 말까"**가 지침 품질을 좌우한다. 아래는 실제로 지침을 망가뜨린 패턴들이다.

## 도구별 로딩 방식 — 안티패턴의 근원

무엇이 언제 읽히는지 모르면 규칙을 엉뚱한 곳에 둔다.

| 파일 | Claude Code | Codex | 비용 |
|---|---|---|---|
| 루트 `AGENTS.md` | `CLAUDE.md` 의 `@AGENTS.md` 로 항상 | 항상 (project-doc) | 매 세션 |
| 하위 `{{모듈}}/AGENTS.md` | 같은 폴더 `CLAUDE.md` bridge 를 통해 해당 디렉터리 파일 접근 시 | 루트→CWD 체인으로 누적 | 해당 작업만 |
| `.claude/rules/*.md` | `paths` 가 맞을 때만 | **안 읽음** | 해당 작업만 |
| `.claude/skills/`, `.agents/skills/` | 이름+설명만 먼저, 발동 시 본문 | 동일 | 설명만 상시 |
| `docs/**` | 지시받아 읽을 때만 | 동일 | 0 |
| `.claude/settings.json`, `.codex/config.toml` | 동작 설정 (프롬프트 아님) | 동일 | 0 |

**핵심**: 조건부 로딩이 되는 건 path-scoped rule 과 하위 디렉터리 지침뿐이다. 일반 import 는 파일만 나눌 뿐 **시작 컨텍스트를 줄이지 못한다.**

## 1. 고정 수치

```markdown
❌ ArchUnit 21 룰 · 583개 테스트 통과 · 도메인 32개
✅ `{{ARCH_TEST_CMD}}` 로 확인 (개수는 실행 결과로)
```

수치는 반드시 틀어진다. 틀어진 문서는 나머지 내용까지 의심받는다.

## 2. 디렉터리 트리 복붙

패키지 구조는 코드를 보면 안다. 지침에 필요한 건 트리가 아니라 **"어디에 둘지 정하는 판정 알고리즘"** 이다.

## 3. 도구별 파일에 상세 규칙 복제

`.claude/rules` 와 `.codex/`, `AGENTS.md` 에 같은 규칙을 각각 적으면 **반드시 갈라진다.** 규칙은 `docs/` 한 곳에 두고 나머지는 참조만 한다.

## 4. 한 번의 실수를 즉시 상시 규칙으로

한 번 겪은 실수는 사고이지 규칙이 아니다. 승격 절차([instruction-maintenance.md](instruction-maintenance.md))를 거친다. 상시 지침은 **재발 가능성 × 피해 크기**가 컨텍스트 비용을 넘을 때만 늘린다.

## 5. 기계가 잡을 수 있는 것을 문장으로

컴파일러·린터·아키텍처 테스트로 강제 가능하면 문서에 쓰지 않는다. 문장은 가장 약한 강제 수단이고, 지키는지 아무도 확인하지 않는다.

## 6. 옵트인 위치에 필수 규칙 두기

`output-styles/` 는 켠 사람에게만 적용된다. `.claude/rules` 는 경로가 맞아야 읽힌다. **치명적 불변식은 루트에 둔다.**

## 7. 일반론

```markdown
❌ 코드는 읽기 쉽게 작성한다 · 적절한 추상화를 유지한다 · SOLID 를 지킨다
✅ {{이 프로젝트에서만 참인, 어겼을 때 무엇이 깨지는지 말할 수 있는 규칙}}
```

모델이 이미 아는 일반 원칙은 컨텍스트만 먹는다.

## 8. 날짜만 갱신하는 gardening

`Last verified` 를 코드 대조 없이 바꾸면, 틀린 문서에 최신 도장을 찍는 셈이라 **아무것도 안 한 것보다 나쁘다.**

## 9. 개인 사정을 공용 지침에

"나는 IntelliJ 를 쓴다", "지금 X 브랜치 작업 중" 은 `CLAUDE.local.md` 로. 판정 기준은 [instruction-maintenance.md](instruction-maintenance.md) 의 공용/개인 표.

## 10. 검증 없는 완료 선언

"통과했습니다"는 명령을 실제로 돌리고 결과를 본 뒤에만 쓴다. 안 돌렸으면 "미실행"이라고 쓴다.

## 자가 점검

- [ ] 실제 실패 사례가 있고 재발 가능성이 있는가?
