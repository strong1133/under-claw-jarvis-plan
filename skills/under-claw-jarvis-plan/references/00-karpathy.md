# 00 · Karpathy 행동 원칙 (전 Phase 상시 적용)

> 출처: Andrej Karpathy의 LLM 코딩 실수 관찰 기반 (multica-ai/andrej-karpathy-skills, MIT).
> 이 원칙은 "이해 도구"가 아니라 **모든 단계(이해/계획/구현/검수)에 상시 적용하는 제약**이다.
> 트레이드오프: 속도보다 신중함에 치우친다. 사소한 작업은 판단껏 생략.

## 1. Think Before Coding — 가정하지 말고, 혼란을 숨기지 말고, 트레이드오프를 드러내라
- 가정은 명시한다. 결과를 바꾸고 스스로 확인할 수 없는 불확실성은 Intake에서 한 번에 모아 묻는다.
- 시작 전에 해석이 갈리면 선택지를 그 질문에 포함한다. 시작한 뒤 갈리면 요청과 자료가 가장 직접 지지하는
  해석 하나를 택해 가정으로 기록하고 진행한다. 말없이 고르지 않는다.
- 더 단순한 길이 있으면 말한다. 필요하면 반대한다.
- 불분명한 점은 무엇이 불분명한지 적고 가정으로 기록한다. 멈추는 조건은 `shared/working-principles.md`의
  두 가지(파괴적이거나 되돌리기 어려운 행동, 사용자가 결정해야 하는 실제 범위 변경)뿐이다.

## 2. Simplicity First — 문제를 푸는 최소 코드. 투기적 코드 금지
- 요청 범위 밖 기능 금지.
- 1회용 코드에 추상화 금지.
- 요청 안 한 "유연성/설정가능성" 금지.
- 불가능한 시나리오용 에러처리 금지.
- 200줄 짰는데 50줄로 되면 다시 쓴다. "시니어가 과하다고 할까?" → 그렇다면 단순화.

## 3. Surgical Changes — 건드려야 할 것만. 내가 만든 흔적만 치운다
- 인접 코드/주석/포맷을 "개선"하지 않는다.
- 안 망가진 것 리팩토링 금지.
- 기존 스타일에 맞춘다(내 취향이 달라도).
- 내 변경이 만든 orphan(import/변수/함수)만 제거. 기존 dead code는 언급만, 삭제는 요청 시.
- 테스트: 바뀐 모든 줄이 사용자 요청으로 직접 추적되는가.

## 4. Goal-Driven Execution — 성공 기준을 정의하고, 검증될 때까지 반복
- 작업을 검증 가능한 목표로 변환:
  - "검증 추가" → "잘못된 입력을 실행해 거부됨을 확인하라"
  - "버그 수정" → "버그를 재현한 뒤, 수정 후 재현되지 않음을 실행으로 확인하라"
  - "X 리팩토링" → "기존 테스트나 전후 실행 결과가 같음을 확인하라"
- 다단계 작업은 간단한 계획을 명시: `단계 → verify: 체크` 형식.
- 테스트 파일을 남길지는 `shared/working-principles.md`의 조건(사용자 요청 또는 프로젝트가 같은 종류의
  테스트를 관리)을 따르고, 확인용 임시 코드는 남기지 않는다.
- 강한 성공기준은 독립적 루프를 가능케 한다. 약한 기준("되게 해줘")은 계속 되묻게 만든다.
